# 2026-09-21 — SarkariHub: government jobs portal (Astro + headless WordPress)

## What was built

A complete government jobs / results portal from the user's master spec. Frontend is
Astro 5 SSR + Tailwind 4 (Node adapter, swappable to Vercel/Netlify); backend is
headless WordPress with ACF + CPT UI, delivered as importable JSON + a PHP snippets
file. Project root: `C:\Users\Malls\WorkBuddy AI\2026-09-21-11-13-49`.

**Frontend (~50 files).** 32 routes across English and Hindi, 7 custom post types,
dark/light theme, AdSense slots reserved from day one, JSON-LD per post type,
hreflang alternates, sitemap with alternates, revalidation webhook, health endpoint,
generated SVG covers, print styles.

**WordPress side (`wordpress/`).** `acf-field-groups.json` (2 groups, 26 fields),
`cptui-post-types.json` (7 types), `cptui-taxonomies.json` (3 taxonomies),
`functions-snippets.php` (settings endpoint, revalidate webhook, hardening, dashboard
rebuild button, ACF/REST misconfiguration warning), plus `README-SETUP.md` and
`plugin-list.md`.

**Verification tooling (`scripts/`).** `mock-wordpress.mjs` (fake WP API with the
awkward payload shapes), `verify.mjs` (81 assertions), `validate-wp-config.mjs`
(ACF/CPT drift detector), `inspect-routes.mjs`.

## Key decisions

- **REST, not WPGraphQL.** One expensive relation (featured media + terms), resolved
  by `?_embed` in the same request. GraphQL would add a plugin and a second cache
  layer for no gain. Reasoning documented in `src/lib/wp.ts`.
- **Deadlines live in the Important Dates repeater**, not a dedicated field — that is
  how these posts are actually written. The frontend finds the "last date" row and
  derives the countdown, badge and `validThrough` from it.
- **`JobPosting` schema only on `jobs`.** Using it on a result page is a schema
  violation that suppresses rich results sitewide.
- **Graceful degradation.** WordPress down → serve the bundled snapshot with a
  visible banner instead of a 500. A stale page beats no page on result day.
- **Local static pages**, not WordPress pages, so an editor cannot accidentally
  unpublish the AdSense-required legal pages.

## Bugs found and fixed during the build (all verified)

1. **Vite inlined the revalidation secret into `dist/` as plaintext.** A literal
   `import.meta.env.REVALIDATE_SECRET` access gets replaced at build time. Fixed by
   splitting `readEnv()` (runtime → build-time) from `readSecret()` (runtime only).
   Verified by grepping `dist/`. See the `astro-headless-cms-frontend` skill.
2. **`readEnv` had an ordering bug**: `import.meta.env.X || process.env.X` never
   falls through, because `""` is falsy but not undefined. Runtime env must be read
   first.
3. **A missing import shipped to a running server** (`readEnv is not defined`) and
   returned HTTP 200 with a 21-byte body, because Astro's Node adapter streams and
   the headers are already flushed. `astro build` does not type-check. Added
   `npm run check` and made `verify.mjs` assert on bodies, not status codes.
4. **`LangSwitch`/`ThemeToggle` were used in `Header.astro` without imports.** Same
   failure mode as (3).
5. **The offline banner showed even when running intentionally on the snapshot.**
   Added `isDegraded()` = configured-but-unreachable.
6. **`formatNumber` was dead code** — a test passed on the title text, not the table.
   Vacancy counts rendered unformatted ("17727" not "17,727").
7. **All sample deadlines were in the past**, so every card read "Closed" and no
   countdown ever rendered. Fixed with per-post date anchoring in `snapshot.ts`.
8. **`.reveal` content could stay permanently invisible** if the IntersectionObserver
   never fired. Added a 2s safety net.
9. Astro's `security.checkOrigin` blocked the webhook (form-encoded POST, no Origin).
   Disabled with reasoning; the endpoint is secret-authenticated, not cookie-based.

## Traps worth remembering

- **A stale server on the port produces false failures.** Twice I tested against an
  old process still holding 4321 and got 404s from superseded code. Kill by port
  before restarting, and check `EADDRINUSE` in stderr.
- **`agent-browser` loses the page between separate shell calls.** Chain
  `open → eval → screenshot` in one call.
- **A full-page screenshot does not scroll**, so `IntersectionObserver` reveals never
  fire and the capture looks empty. Wait out the safety net before capturing.
- Use `--noproxy '*'` with curl; a proxy is configured and otherwise returns 502.

# Round 2 — performance, VPS deployment, CI

## Performance measured (was the biggest stated gap)

`agent-browser vitals` reads Core Web Vitals from the browser's Performance API —
no Lighthouse install needed. Mobile 390x844, production build:

| Page | TTFB | LCP | CLS |
|---|---|---|---|
| Homepage | 25–37ms | 148ms | 0.01 |
| Post page | 32ms | 340ms | 0 |
| /hi | 32ms | 288ms | 0 |

**The fix that mattered:** cold-load LCP was 2352ms against a 25ms server response.
Cause: a plain `<link rel="stylesheet">` to fonts.googleapis.com is render-blocking —
the browser resolves a third-party origin, downloads CSS, then the woff2, before
painting anything. Switching to the async pattern (`media="print"` + `onload` +
`<noscript>` fallback) took cold LCP **2352ms → 1184ms**. Added a metric-matched
`Inter Fallback` `@font-face` (size-adjust 107.11%, ascent/descent overrides) so the
swap does not shift layout — CLS stayed at 0.

**Measurement floor, worth remembering:** a tiny JSON endpoint on a fresh browser
session reports FCP 760ms. So ~700ms of any cold-session number is browser launch,
not the page. Only compare cold-to-cold, and use warm (3rd load in a session) as the
steady-state figure. Without this I would have chased a phantom 700ms.

**Honesty note:** these are not Lighthouse scores. Lighthouse also applies ~4x CPU
throttling and Slow 4G, and folds in a11y/best-practices/SEO. Documented as such in
the README rather than claimed as "Lighthouse 90+".

## Added

# Round 3 — Lighthouse, real scores, and the a11y fixes it exposed

## Lighthouse actually run

Installed `lighthouse` + `chrome-launcher` locally; used the system Chrome at
`C:\Program Files\Google\Chrome\Application\chrome.exe` via `CHROME_PATH`. Mobile
preset, simulated throttling, production build.

| Page | Perf | A11y | BP | SEO |
|---|---|---|---|---|
| Homepage | 95 | 100 | 100 | 100 |
| Post page | 90 | 100 | 100 | 100 |
| Hindi homepage | 89 | 100 | 100 | 100 |

Started at Perf 87 / A11y 83 on the homepage. Everything else is now 100.

## The diagnostic that cracked it

Rather than guessing at LCP, I A/B'd it: ran Lighthouse with
`--blocked-url-patterns="*fonts.gstatic.com*"`.

    Google Fonts linked    Performance 87   LCP 3.6s   TBT 210ms
    Web fonts blocked      Performance 98   LCP 2.0s   TBT   0ms

That isolated the entire gap to the third-party font origin, and showed it was not
just latency — the hero `<h1>` is the LCP element, paints in the fallback face, and
the repaint when the webfont arrives registers as a *later* LCP candidate.

**Blocking a resource to measure its cost is a technique worth reusing.** It is far
faster than reading traces.

Fix: self-hosted fonts via `scripts/fetch-fonts.mjs` (downloads only the Latin and
Devanagari subsets, writes `src/styles/fonts.css`, preloads the LCP-critical woff2).

## Real accessibility bugs found (all fixed)

1. **Unnamed mobile search button.** Visible label is `hidden` below `sm`, icon is
   `aria-hidden` → no accessible name at all on mobile. Added `aria-label`.
2. **`<dl>` content model violation.** A `<div>` inside `<dl>` may contain ONLY
   `dt`/`dd`. My decorative `<span>` icon broke it, and nesting `dt`/`dd` one level
   deeper also fails `dlitem`. Fixed with grid placement so dt/dd are direct children.
3. **Dark-mode contrast.** White on `--accent: #ff9d3d` was **2.07:1** — the accent
   button was effectively unreadable. Added an `--accent-ink` token (white in light,
   near-black in dark). Also lightened dark `--brand` (#4b83ff → #5389ff) so the
   brand pill cleared 4.5:1 against `--brand-soft`.
4. **`h2 → h4` heading skip** in the sidebar (compact PostCard used `h4`).
5. Light `--ink-3` was 4.24:1 — darkened to `#5d6a84` (5.44:1).

Lesson: **check contrast in BOTH themes.** Lighthouse flagged the dark values while
I had only verified light.

## Rejected after measuring

`inlineStylesheets: 'always'`: Perf 95 with it vs 96 without, HTML 152 KB vs 98 KB.
Reverted. Worth remembering that "removes a render-blocking request" is not
automatically a win.

## Main-thread anti-patterns removed

- `will-change: transform` on every card — promotes ~40 elements to compositor
  layers; Chrome caps the count and silently ignores the hint past that, so the cost
  is paid and the benefit is not.
- Reading-progress bar transitioned `width` → re-ran document layout on every scroll
  frame. Now `transform: scaleX()` (compositor-only).

## Build trap discovered

The build **hung** (not failed) for 11 minutes because the running Node server held
`dist/` open on Windows. Moving `dist` aside first fixes it. Earlier the same guard
manifested as an error; a hang is the other face of it. **Always stop the server
before rebuilding on Windows.**

## Honest remaining gap

Hindi homepage Performance 89, one point under target. Cause identified: 290 ms of
Style & Layout from re-laying out Devanagari text when the 118 KB font arrives. The
proper fix is font subsetting with `fonttools`; the cheap alternative (system
Devanagari font) would trade reading quality for a score point. Documented rather
than papered over.

## The fix that closed it: static vs variable font instances

The Hindi page was 89 with 8 points attributable to the Devanagari font (blocking
`*/fonts/*` gave 97). Subsetting alone only bought 12%. The real win was
**variable vs static**:

| | variable | static |
|---|---|---|
| Inter, 5 weights | **47 KB** | ~60 KB |
| Devanagari, 2 weights | 118 KB | **96 KB (19% less)** |

A variable font ships every weight plus a `gvar` delta table — worth it at five
weights, a loss at two. Switching Devanagari to static 400/700 instances:
**Hindi homepage 89 → 95, TBT 300 ms → 10 ms** (static faces skip delta work at
render time). Inter stays variable.

The choice is now per-family in `scripts/fetch-fonts.mjs`, and the script picks
the cheaper form automatically.

## Two traps caught by checking rather than assuming

1. **A mis-parsed unicode-range produced a 600-byte font.** I almost shipped it —
   it looked like a 99% size win. The script now refuses any subset below 15% of
   its source download. An absolute byte floor does not work (the `latin` subset
   of a Devanagari font is legitimately ~10 KB), so the check is a ratio.
2. **Renaming a font file silently broke the hand-written preload.** Switching to
   static instances renamed four files; the `<link rel="preload">` in BaseLayout
   would have 404'd, the font would arrive late, and the LCP regression would look
   mysterious. Preload paths are now **generated** into `src/lib/font-preloads.ts`
   from the same data that names the files. The script also deletes orphaned
   fonts from `public/fonts` so renamed files don't ship forever.

## Remaining caveats (documented in the README)

- Lighthouse covers one representative page per route type, not every URL.
- `npm run fonts` needs Python + fonttools for the static instances; without it it
  falls back to the variable font (site works, Hindi ~22 KB heavier).
- Hindi post page CLS 0.026 (good threshold is <0.1) from the bold Devanagari swap.
  Not chased — the fix would be a metric-matched Devanagari fallback face.
- No real WordPress, `deploy/` unexecuted, `REVALIDATE_SECRET` still a placeholder.

# Round 5 — audited all 38 pages; that found a CLS failure one-per-type missed

## Final: 38 pages, mean Perf 96 / A11y 100 / BP 100 / SEO 98, CLS 0 everywhere

Every category ≥90 on every page. Worst CLS anywhere: **0**.

## Why the full sweep mattered

Auditing one page per route type was not enough. `/hi/admit-card` and
`/hi/admit-card/{slug}` share every component and differ only in content:

| Page | CLS (original) |
|---|---|
| `/hi/admit-card` (listing) | **0.191** — poor |
| `/hi/admit-card/ssc-mts-havaldar-2026-admit-card` (post) | 0.001 |

Only the listing was bad, and only the full sweep found it. This directly
invalidated the "one page per route type is representative" assumption I had
written into the README.

## The metric-matched fallback did not work — and made a second page worse

I built a metric-matched Devanagari fallback the textbook way: measured Nirmala UI
in the browser (renders Hindi **10% wider** than Noto Sans Devanagari →
`size-adjust: 90.57%`), derived the overrides from the font's own hhea metrics
(ascent 0.896 em, descent 0.408 em), sanity-checked that
`ascent-override × size-adjust` equalled the web font's ascent.

Result:
- `/hi/admit-card`: 0.191 → **0.001** ✓
- `/hi/admit-card/{slug}`: 0.001 → **0.153** ✗ — it broke a page that was fine

**A single measured ratio is not a metric match.** Devanagari line-breaking varies
enough between strings that some pages still reflow. I traded one page's CLS for
another's and only the full audit caught it.

## What actually worked: `font-display: optional`

Switching the Devanagari faces to `optional` removed the reflow instead of
shrinking it — the browser uses the fallback for the whole page load and never
swaps. **CLS 0 on every Hindi page**, Perf 90–97. The font is still downloaded and
cached, so it applies from the second page onward, and Hindi readers of a jobs
portal are repeat visitors. Nirmala UI (Windows) and Noto Sans Devanagari
(Android, where it is the system font anyway) are both legible.

Inter keeps `swap` — its metric-matched fallback *is* verified (homepage holds
CLS 0 with Inter swapping) and Inter text is on the LCP path.

Removed the Devanagari Fallback face entirely and recorded the rationale in
`global.css`, so nobody rebuilds it from the same wrong assumption.

**Lesson:** when a fix is derived from a measurement, test it on more than the
page you measured. And prefer a fix that removes a failure class over one that
shrinks it — `optional` needs no metric tuning, no platform scoping, and cannot
be wrong per-string.

# Round 6 — validated the deploy config (it had two real bugs)

## `npm run deploy:check` — static validation, no Docker or nginx needed

`scripts/validate-deploy.mjs`, 23 checks, wired into CI. It found two bugs that
would only have shown up in production:

**1. nginx served static assets from a directory that does not exist.**
`deploy/nginx.conf` aliased `/srv/sarkarihub/client/_astro/`, but
`deploy/ecosystem.config.cjs` runs the app with `cwd: /srv/sarkarihub/app`, so the
real path is `/srv/sarkarihub/app/dist/client/_astro/`. This fails *silently*:
nginx 404s the asset and falls through to the Node proxy, so the site still works —
just slower, with no error anywhere. Fixed, and the validator now derives the
expected root from the PM2 `cwd` and checks every `alias`/`root` against it.

**2. No `.dockerignore`, while the Dockerfile runs `COPY . .`.** That sends the
whole working directory — including `.env`, with `REVALIDATE_SECRET` and the
WordPress application password — into the build stage. Same class of leak as the
Vite `import.meta.env` bug from round 1, in a different layer. Also copies
`node_modules` over the layer the Dockerfile had just installed. Added
`.dockerignore`.

## A third finding: `alias` cannot reach into a container

The nginx config's static-asset blocks only work for the PM2 path. With Docker,
nginx on the host cannot read a path inside the container, so those two
`location` blocks would 404. Documented in both `nginx.conf` and `deploy/README.md`
with the two ways out (bind-mount the output, or proxy everything).

## Lesson: check your checker

The first version of the validator reported a false failure on a correct compose
file. `dockerfile` in compose is relative to the **context**, not to the compose
file's directory — `context: ..` + `dockerfile: deploy/Dockerfile` resolves to
`deploy/Dockerfile`, not `deploy/deploy/Dockerfile`. A validator that is wrong
teaches people to ignore it, which is worse than none. Recorded in the
`verify-docker-deploy-without-docker` skill along with the two path-resolution
rules that are easy to invert.
